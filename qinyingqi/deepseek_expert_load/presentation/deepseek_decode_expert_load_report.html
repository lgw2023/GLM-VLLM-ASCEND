方案演进：从 Full-Phase 采集失败到 Decode-Trusted 可交付路径

v4–v9 补丁迭代说明：为何最终汇报选择 decode-only
v4–v5 先跑通 benchmark；decode 路由干净，prefill 在 TP-split 后采集。
劣势：prefill 大面积 zero / duplicate。
v6–v8 尝试在 capturer 内 gather / 在 prepare 前采集。
劣势：prefill 仍不可信；部分请求 capturer 未绑定。
v9 prepare() 前 select_experts + bind 修复 + TP gather 诊断。
优势：定位问题清晰；decode 可用于正式分析。
本轮交付 `--unique-scope decode` 跑完四类 benchmark。
优势：不阻塞 expert load 结论；可立即汇报。

Prefill 失败机理（Ascend 特有）

  • `PrepareAndFinalizeWithAll2All` 在 TP>1 时将 prefill token 切到各 rank。
  • 若采集点位于 split 之后，仅约 1/TP 行是真实 logical route。
  • 表现：`all_zero_cell_fraction ≈ duplicate_cell_fraction`，且 decode_dup 仍为 0。
  • 这与 FLASHCOMM1=0 不矛盾，是 MoE 通信路径问题。

Decode 为什么可信

  • Decode 每步仅 1 个 token，不会触发 prefill 式 batch split。
  • 诊断日志常见：`topk=(1, 6)` 且 `decode_dup=0.0000`。
  • `route-quality.json` 可标记 `routes_trusted_for_decode_load_analysis=true`。
  • 对“生成阶段算力如何分配”这一问题，decode 更具代表性。
总结
  • 不是实验失败，而是 相位可信度分层：decode 可交付，prefill 待修复。
  • 汇报中必须写清“decode-trusted contract”，避免被质疑数据有效性。
  • 后续若 prefill 修复成功，可追加 total-phase 对比作为二期工作。

风险与局限：Decode-Trusted 结论可汇报，但还不能直接指导 Full-Sequence 放置

明确交付边界，避免过度解读

数据质量与代表性风险

风险项现状影响缓解
Prefill 路由不可信 TP-split 污染 total 相位误导 只报 decode；二期修 v9+ prefill
样本规模有限 {{MAX_REQUESTS}} req/benchmark 统计波动 扩到 50 条/full workload
Decode 长度偏短 曾用 128 tokens CoT 未充分展开 提升到 1024/2048 并重跑
ignore_eos=true 脚本默认开启 与自然停词行为不一致 后续改为 false 做对照

指标使用边界

  • 可用于汇报：decode 相位热点集中度、跨 benchmark 差异趋势。
  • 暂不可用：prefill 相位、total 相位、端到端 SLA 推导。
  • Expert ID 在不同层不是同一权重，pooled expert-ID 指标仅作诊断。
  • 本实验未开启 EPLB / 动态负载均衡，测的是基线路由偏斜。

建议补充实验

  1. 扩大样本量到每类 50 条，观察集中度是否稳定。
  2. 对比不同 max_tokens（128 vs 1024）对 decode 热点的影响。
  3. 若 prefill 修复，补做 total-phase 与 decode-phase 一致性分析。
总结
  • 当前结论适合作为“生成阶段 expert 负载基线”。
  • 不宜直接外推到完整上下文预填充阶段的 HBM 策略。
  • 汇报时应把局限写成正式合同，而不是隐藏 caveat。

结论与建议：基于 Decode 相位建立 DeepSeek Expert 负载基线

现状 / 问题 / 建议 / 预期收益

现状

  • 已在 Ascend 910B1×8 上跑通 DeepSeek-V4 W8A8 路由采集与四类 benchmark。
  • Decode 路由通过唯一性校验，形成可分析的 aggregate / report 产物。
  • 主命题验证结果：{{H1_VERDICT}}

问题

  • Prefill 在 TP=8 下仍不可信，total 相位不能用于正式结论。
  • 当前样本规模与 decode 长度可能不足以覆盖长 CoT 场景。

建议

  1. 短期：以 decode 相位作为 expert load 基线，完成汇报与内部评审。
  2. 中期：扩 benchmark 到 50 条/类，并将 max_tokens 提升到 1024+。
  3. 长期：继续修 prefill capture（v9+），补 total-phase 分析。
  4. 若热点集中成立，评估静态热点 expert 放置、冗余副本和 EPLB 配置。

预期收益

  • 为 MoE 部署提供任务域相关的 expert 负载画像。
  • 支撑“20% expert / 90% load”是否成立的工程判断。
  • 为后续 Ascend 上 expert parallel / 内存优化提供数据依据。
总结
  • 这次实验已经能回答：生成阶段 expert 是否高度集中、不同 benchmark 是否路由不同。
  • 汇报时只引用 decode 指标，并明确 prefill 尚未修复。
  • 下一步优先扩样本与加长 decode，而不是等待 prefill 完美后再汇报。
